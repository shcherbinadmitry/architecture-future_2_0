# Целевая архитектура "Будущее 2.0" - Упрощённая диаграмма
## Ключевые особенности архитектуры

### Решение проблем

| Проблема                      | Как решается                                         |
|-------------------------------|------------------------------------------------------|
| **Низкая производительность** | Data Lakehouse с columnar storage → отчёты за минуты |
| **Монолитное хранилище**      | Разделение на 4 домена с собственными БД             |
| **Связанность логики**        | Микросервисы в каждом домене, API-first подход       |
| **Отсутствие изоляции**       | Независимые домены с собственной инфраструктурой     |
| **ESB - точка отказа**        | Event Bus (Kafka) + распределённая архитектура       |
| **Нет self-service**          | Портал самообслуживания + Data Catalog               |
| **Нет облака**                | Полная миграция в облачную инфраструктуру            |

### Потоки данных

#### Операционные данные (OLTP)
```
Пользователь → API Gateway → Доменный API → Доменный сервис → Доменная БД
```

#### Аналитические данные (OLAP)
```
Доменная БД → Data Product → ETL → Data Lakehouse → BI/Портал → Пользователь
```

#### Межсервисное взаимодействие
```
Домен A → Event Bus (Kafka) → Домен B
```

### Архитектурные принципы

1. **Data Mesh**
   - Децентрализованное владение данными
   - Data as a Product
   - Self-service платформа
   - Federated governance

2. **Domain-Driven Design**
   - Медицинский домен
   - Финтех домен
   - Операционный домен
   - ИИ домен

3. **Event-Driven Architecture**
   - Асинхронная интеграция через Kafka
   - Слабая связанность
   - Отказоустойчивость

4. **API-First**
   - Все взаимодействия через API
   - Версионирование API
   - API Gateway для управления

### Бизнес-сценарии

#### 1. Быстрая подготовка отчётности
- **Было:** Часы
- **Стало:** Минуты
- **Как:** Data Lakehouse + предварительно подготовленные Data Products

#### 2. Независимое развитие направлений
- **Было:** Изменения в DWH влияют на все системы
- **Стало:** Каждый домен развивается независимо
- **Как:** Изоляция доменов + API-first

#### 3. Масштабирование для новых бизнесов
- **Было:** Месяцы на интеграцию
- **Стало:** Недели
- **Как:** Стандартизированный подход + облачная инфраструктура

#### 4. Self-service аналитика
- **Было:** Все запросы через IT
- **Стало:** 80%+ отчётов создаются бизнесом
- **Как:** Портал самообслуживания + Data Catalog

#### 5. Безопасность и compliance
- **Было:** Смешение всех данных
- **Стало:** Изоляция чувствительных данных
- **Как:** Доменная архитектура + Data Governance

#### 6. Отказоустойчивость
- **Было:** ESB и DWH - единые точки отказа
- **Стало:** Доступность 99.9%+
- **Как:** Распределённая архитектура + облако

### Важные замечания

1. **Медицинские карты и истории болезней НЕ попадают в аналитическую витрину** - только агрегированные и обезличенные данные

2. **Legacy системы сохраняются временно** - постепенный вывод из эксплуатации в течение года

3. **Облачная инфраструктура** - основа для масштабирования и отказоустойчивости

4. **Data Governance** - критично для соответствия регуляторным требованиям

5. **Event-driven архитектура** - обеспечивает слабую связанность и отказоустойчивость

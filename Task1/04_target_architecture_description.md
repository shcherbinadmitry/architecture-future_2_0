# Целевая архитектура "Будущее 2.0" - Описание

## Обзор

## Пользователи и системы, через которые они работают

В целевой архитектуре каждая роль пользователя взаимодействует с платформой через определённые системы и интерфейсы. Ниже описаны ключевые роли и цепочки систем, обеспечивающих их работу.

### Врач

**Основная система:** Клинический портал (React/Vue.js) — современный веб-интерфейс, заменяющий устаревший PowerBuilder.

**Цепочка взаимодействия:**
```
Врач → Клинический портал (React/Vue.js) → API Gateway (Kong/Apigee) → Клинический домен (FastAPI/Spring Boot + PostgreSQL)
                                                                       → Медицинский домен (FastAPI + PostgreSQL + S3/MinIO)
                                                                       → ИИ-домен (FastAPI + MLflow)
```

**Какие системы задействованы и зачем:**

| Система                | Технология                                        | Назначение для врача                                                    |
|------------------------|---------------------------------------------------|-------------------------------------------------------------------------|
| **Клинический портал** | React/Vue.js                                      | Просмотр расписания, управление приёмами, регистрация пациентов         |
| **API Gateway**        | Kong/Apigee                                       | Единая точка входа, аутентификация, маршрутизация запросов              |
| **Клинический домен**  | Python/FastAPI или Java/Spring Boot + PostgreSQL  | Расписание приёмов, профили пациентов, данные о клиниках                |
| **Медицинский домен**  | Python/FastAPI + PostgreSQL + S3/MinIO            | Медицинские карты, истории болезней, результаты исследований, снимки    |
| **ИИ-домен**           | Python/FastAPI + MLflow + GPU-инстансы            | Запрос ИИ-анализа снимков, получение результатов предиктивной аналитики |

**Сценарии работы:**
- Просмотр расписания приёмов на день → Клинический портал → Клинический домен
- Просмотр истории болезни пациента → Клинический портал → API Gateway → Медицинский домен
- Запрос ИИ-анализа снимка → Клинический портал → API Gateway → ИИ-домен → Медицинский домен (получение снимка) → ИИ-домен (результат)
- Просмотр результатов исследований → Клинический портал → API Gateway → Медицинский домен

> **Временно:** На переходном этапе врач может продолжать работать через legacy-интерфейс (PowerBuilder), который подключён к старому DWH. По мере миграции все функции переносятся в клинический портал.

### Оператор клиники

**Основная система:** Клиентский интерфейс оператора (React/Vue.js) — полная замена PowerBuilder.

**Цепочка взаимодействия:**
```
Оператор → Клиентский интерфейс оператора (React/Vue.js) → API Gateway (Kong/Apigee) → Клинический домен (FastAPI/Spring Boot + PostgreSQL)
```

**Какие системы задействованы и зачем:**

| Система                            | Технология                                       | Назначение для оператора                                     |
|------------------------------------|--------------------------------------------------|--------------------------------------------------------------|
| **Клиентский интерфейс оператора** | React/Vue.js                                     | Регистрация пациентов, запись на приём, управление очередями |
| **API Gateway**                    | Kong/Apigee                                      | Единая точка входа, аутентификация, маршрутизация            |
| **Клинический домен**              | Python/FastAPI или Java/Spring Boot + PostgreSQL | Профили пациентов, расписание, записи на приём               |
| **Redis (кэш)**                    | Redis                                            | Кэширование расписания для быстрого отклика интерфейса       |

**Сценарии работы:**
- Регистрация нового пациента → Клиентский интерфейс → API Gateway → Клинический домен (PostgreSQL)
- Запись пациента на приём → Клиентский интерфейс → API Gateway → Клинический домен (Redis + PostgreSQL)
- Управление очередью пациентов → Клиентский интерфейс → API Gateway → Клинический домен
- Просмотр и редактирование расписания врачей → Клиентский интерфейс → API Gateway → Клинический домен

> **Временно:** На переходном этапе оператор может работать через PowerBuilder, подключённый к legacy DWH. Замена PowerBuilder на современный веб-интерфейс — одна из приоритетных задач миграции.

### Финансовый специалист

**Основная система:** Финансовый интерфейс (веб-приложение) — работа с финтех-доменом, а также аналитический портал для отчётности.

**Цепочка взаимодействия:**
```
Финансовый специалист → Финансовый интерфейс (веб) → API Gateway (Kong/Apigee) → Финтех домен (Go/Java + PostgreSQL + Kafka)
                      → Портал самообслуживания (React/Vue.js) → Data Lakehouse (Databricks/Snowflake) → BI (Tableau/Looker)
```

**Какие системы задействованы и зачем:**

| Система                     | Технология                   | Назначение для финансового специалиста                             |
|-----------------------------|------------------------------|--------------------------------------------------------------------|
| **Финансовый интерфейс**    | Веб-приложение               | Управление счетами, обработка платежей, кредитование, биллинг      |
| **API Gateway**             | Kong/Apigee                  | Единая точка входа, аутентификация, маршрутизация                  |
| **Финтех домен**            | Go/Java + PostgreSQL + Kafka | Счета клиентов, транзакции, кредитные договоры, финансовая история |
| **Портал самообслуживания** | React/Vue.js                 | Построение финансовых отчётов, дашборды с KPI                      |
| **Data Lakehouse**          | Databricks/Snowflake         | Агрегированные финансовые данные для аналитики                     |
| **BI-инструменты**          | Tableau/Looker               | Визуализация финансовой отчётности, дашборды                       |

**Сценарии работы:**
- Обработка платежа за медицинские услуги → Финансовый интерфейс → API Gateway → Финтех домен (PostgreSQL + Kafka)
- Оформление кредита на лечение → Финансовый интерфейс → API Gateway → Финтех домен
- Формирование финансовой отчётности → Портал самообслуживания → Data Lakehouse → BI (Tableau/Looker)
- Расчёт стоимости лечения по страховке → Финансовый интерфейс → API Gateway → Финтех домен
- Консолидированная отчётность по выручке → Портал самообслуживания → Data Lakehouse (Data Products из всех доменов)

 **Безопасность:** Финансовые данные изолированы в финтех-домене, который соответствует требованиям PCI DSS и регуляторным требованиям ЦБ. Доступ к финансовым данным строго контролируется через API Gateway с аутентификацией и авторизацией.

## Поддержка ключевых бизнес-сценариев

### 1. Быстрая подготовка отчётности

**Проблема:** Отчёты формируются часами

**Решение в целевой архитектуре:**

#### Data Lakehouse с оптимизацией
- **Columnar storage** (Parquet/Delta Lake) - быстрое чтение аналитических запросов
- **Партиционирование** данных по времени и другим измерениям
- **Z-ordering** для оптимизации запросов
- **Кэширование** часто используемых данных
- **Материализованные представления** для сложных агрегаций

**Результат:** Время формирования отчётов сокращается с часов до **минут или секунд**

#### Предварительно подготовленные Data Products
- Каждый домен публикует **очищенные и агрегированные** данные
- Данные уже оптимизированы для аналитики
- Не требуется сложных JOIN'ов в момент запроса

**Результат:** Бизнес-пользователи работают с **готовыми к анализу** данными

#### Масштабирование compute ресурсов
- Облачная инфраструктура позволяет **динамически масштабировать** вычислительные ресурсы
- Отдельные compute кластеры для разных типов нагрузки
- Auto-scaling при пиковых нагрузках

**Результат:** Производительность не падает при **одновременной работе** множества пользователей

### 2. Независимое развитие финтех- и ИИ-направлений

**Проблема:** Все изменения требуют модификации центрального DWH

**Решение в целевой архитектуре:**

#### Изоляция доменов
- Каждый домен имеет **собственную БД** и инфраструктуру
- Изменения в одном домене **не влияют** на другие
- Независимые команды разработки

**Результат:** Финтех может добавлять новые продукты **без согласования** с медицинским доменом

#### API-first подход
- Домены взаимодействуют через **стабильные API**
- Внутренняя реализация может меняться без влияния на потребителей
- Версионирование API для обратной совместимости

**Результат:** Снижение **Time-to-Market** для новых функций

#### Event-driven интеграция
- Асинхронный обмен событиями через Kafka
- Слабая связанность между доменами
- Каждый домен подписывается только на нужные события

**Результат:** Добавление нового домена **не требует изменений** в существующих

### 3. Масштабирование для новых бизнесов

**Проблема:** Сложность интеграции новых направлений (фармацевтика, производство оборудования)

**Решение в целевой архитектуре:**

#### Стандартизированный подход к добавлению доменов
1. Создать новый домен с собственной инфраструктурой
2. Реализовать API по общим стандартам
3. Опубликовать Data Product в Data Lakehouse
4. Зарегистрировать в Data Catalog

**Результат:** Новый бизнес интегрируется за **недели, а не месяцы**

#### Переиспользование платформенных сервисов
- API Gateway
- Data Catalog
- Data Governance
- Мониторинг и логирование
- Аутентификация и авторизация

**Результат:** Новым доменам **не нужно создавать** инфраструктуру с нуля

#### Облачная инфраструктура
- Быстрое выделение ресурсов для нового домена
- Изолированные среды (dev, test, prod)
- Infrastructure as Code (Terraform/CloudFormation)

**Результат:** Инфраструктура для нового домена разворачивается за **часы**

### 4. Self-service аналитика

**Проблема:** Бизнес-пользователи зависят от IT-отдела для получения отчётов

**Решение в целевой архитектуре:**

#### Портал самообслуживания
- Интуитивный интерфейс для поиска данных
- Сохранение и шаринг отчётов
- Scheduled отчёты и алерты

**Результат:** Бизнес-пользователи **самостоятельно** получают нужные данные

#### Data Catalog
- Поиск данных по ключевым словам
- Описание датасетов и полей
- Примеры использования
- Контакты владельцев данных

**Результат:** Пользователи **быстро находят** нужные данные

#### Контроль доступа на уровне данных
- Row-level security
- Column-level security

**Результат:** Пользователи видят только **разрешённые** данные

### 5. Обеспечение безопасности и соответствия регуляторным требованиям

**Проблема:** Смешение медицинских и финансовых данных, риски безопасности

**Решение в целевой архитектуре:**

#### Изоляция чувствительных данных
- Медицинские карты и истории болезней **НЕ попадают** в аналитическую витрину
- Финансовые данные изолированы в финтех домене
- Персональные данные маскируются или анонимизируются

#### Аудит и мониторинг
- Логирование всех обращений к данным
- Алерты при подозрительной активности
- Регулярные отчёты для compliance

**Результат:** Возможность **доказать соответствие** регуляторам

#### Шифрование
- Шифрование данных в покое (at rest)
- Шифрование данных в движении (in transit)
- Управление ключами шифрования

**Результат:** Защита от **утечек данных**

### 6. Отказоустойчивость и высокая доступность

**Проблема:** ESB и DWH - единые точки отказа

**Решение в целевой архитектуре:**

#### Распределённая архитектура
- Отказ одного домена **не влияет** на другие
- Kafka обеспечивает гарантированную доставку событий
- Репликация данных между зонами доступности

**Результат:** Доступность **99.9%+**

#### Облачная инфраструктура
- Автоматическое восстановление при сбоях
- Geo-распределение для disaster recovery
- Резервное копирование с автоматическим восстановлением

#### Graceful degradation
- При отказе аналитики операционные системы продолжают работать
- Кэширование для критичных данных
- Fallback механизмы

**Результат:** Бизнес **не останавливается** при частичных сбоях

## Заключение

Целевая архитектура решает все ключевые проблемы текущей системы:

**Производительность** - отчёты за минуты вместо часов
**Масштабируемость** - легко добавлять новые домены
**Независимость** - домены развиваются автономно
**Self-service** - бизнес работает с данными самостоятельно
**Безопасность** - изоляция чувствительных данных
**Отказоустойчивость** - нет единых точек отказа
**Облако** - гибкое масштабирование и снижение затрат

# Обоснование конфигурации Terraform (Docker)

## 1. Почему Docker вместо облачного провайдера

### 1.1. Преимущества локального Docker-развёртывания

| Аспект                | Облако (Yandex Cloud)        | Docker (локально)             |
|-----------------------|------------------------------|-------------------------------|
| **Стоимость**         | ~150-300 тыс. ₽/мес (13 VM)  | Бесплатно                     |
| **Скорость запуска**  | 15-30 минут                  | 1-2 минуты                    |
| **Доступность**       | Нужен интернет + токен       | Работает офлайн               |
| **Воспроизводимость** | Зависит от квот и региона    | 100% воспроизводимо           |
| **Тестирование**      | Дорого для dev/staging       | Бесплатно, неограниченно      |
| **Удаление**          | `terraform destroy` (минуты) | `terraform destroy` (секунды) |

### 1.2. Маппинг облачных ресурсов на Docker

| Облачный ресурс     | Docker-аналог                  | Обоснование                                                                                                          |
|---------------------|--------------------------------|----------------------------------------------------------------------------------------------------------------------|
| **VPC + подсети**   | Docker Network (bridge)        | Docker DNS обеспечивает резолвинг по имени контейнера. Единая сеть заменяет 4 подсети - для dev-окружения достаточно |
| **VM с PostgreSQL** | Контейнер `postgres:16-alpine` | Полная функциональность PostgreSQL. Alpine-образ минимизирует размер                                                 |
| **VM с Kafka**      | Контейнер `apache/kafka:3.7.0` | KRaft mode - без ZooKeeper. Кластер из 3 брокеров для тестирования репликации                                        |
| **S3 Buckets**      | MinIO контейнер                | 100% совместимость с S3 API. Web Console для управления бакетами                                                     |
| **ALB**             | Nginx контейнер                | Reverse proxy с маршрутизацией. Для dev достаточно                                                                   |
| **Security Groups** | Docker Network isolation       | Контейнеры изолированы в bridge-сети. Доступ извне только через проброшенные порты                                   |
| **NAT Gateway**     | Docker bridge NAT              | Docker автоматически обеспечивает NAT для контейнеров                                                                |
| **Bastion Host**    | Не нужен                       | Прямой доступ к контейнерам через `localhost:port`                                                                   |
| **GPU Node**        | Не эмулируется                 | GPU-вычисления невозможны в стандартном Docker. Для dev используется CPU-fallback                                    |
| **DNS Zone**        | Docker internal DNS            | Контейнеры доступны по имени (`future20-pg-clinic`) внутри сети                                                      |

## 2. Выбор ресурсов и параметров

### 2.1. PostgreSQL - 4 контейнера (по одному на домен)

| Домен        | Контейнер             | Порт   | БД         | Пользователь   |
|--------------|-----------------------|--------|------------|----------------|
| Клинический  | `future20-pg-clinic`  | 5433   | clinic     | clinic_user    |
| Финтех       | `future20-pg-fintech` | 5434   | fintech    | fintech_user   |
| Операционный | `future20-pg-ops`     | 5435   | operations | ops_user       |
| Мед. данных  | `future20-pg-medical` | 5436   | medical    | medical_user   |

**Обоснование:**
- **Изоляция доменов** - каждый домен имеет свою БД в отдельном контейнере, что соответствует принципам Data Mesh
- **Отдельные порты** - позволяют подключаться к каждой БД независимо
- **Named Volumes** - данные сохраняются при перезапуске контейнеров
- **Healthcheck** - `pg_isready` проверяет доступность каждой БД
- **postgres:16-alpine** - последняя стабильная версия, минимальный размер образа (~80 MB)

### 2.2. Kafka - 3 брокера

**Обоснование:**
- **3 брокера** - минимум для тестирования репликации (replication factor = 3)
- **apache/kafka** - официальный образ от Apache Foundation
- **Отдельные порты** (9092, 9093, 9094) - для внешнего доступа к каждому брокеру
- **Named Volumes** - сохранение данных топиков между перезапусками

### 2.3. MinIO - S3-совместимое хранилище

**Обоснование:**
- **Полная совместимость с S3 API** - код, написанный для MinIO, работает с AWS S3 / Yandex Object Storage без изменений
- **Web Console** (порт 9011) - удобное управление бакетами через браузер
- **Один контейнер** - достаточно для dev-окружения (в проде - распределённый кластер)
- Заменяет 4 S3-бакета: `medical-images`, `ml-models`, `data-lakehouse`, `backups`

### 2.4. Kong API Gateway

**Обоснование:**
- **DB-less mode** - не требует отдельной БД, конфигурация через YAML
- **Proxy** (порт 8000) - точка входа для API-запросов
- **Admin API** (порт 8001) - управление маршрутами и плагинами
- Заменяет облачный API Gateway

### 2.5. Prometheus + Grafana

**Обоснование:**
- **Prometheus** - сбор метрик со всех контейнеров
- **Grafana** - визуализация метрик, дашборды
- **Named Volumes** - сохранение данных и дашбордов

### 2.6. Nginx (Reverse Proxy)

**Обоснование:**
- Эмулирует Application Load Balancer (ALB)
- Маршрутизация HTTP-трафика к Kong и другим сервисам
- Порт 80 - стандартный HTTP

## 3. Сеть

### Docker Network

```
Сеть: future20-network
Тип: bridge
CIDR: 172.28.0.0/16
Gateway: 172.28.0.1
```

**Обоснование:**
- **Bridge network** - стандартный тип для локальной разработки
- **Custom network** (не default bridge) - обеспечивает DNS-резолвинг по имени контейнера
- **CIDR 172.28.0.0/16** - не конфликтует со стандартными Docker-сетями (172.17-19.x.x)
- Все контейнеры в одной сети - могут общаться по имени (например, `future20-pg-clinic:5432`)

### Изоляция в Docker vs Облако

| Облако                            | Docker                                      |
|-----------------------------------|---------------------------------------------|
| 4 подсети (public, app, data, ai) | 1 bridge network                            |
| 6 Security Groups                 | Порты проброшены только для нужных сервисов |
| NAT Gateway                       | Docker bridge NAT (автоматически)           |
| Bastion Host                      | Не нужен (localhost)                        |

## 4. Причины использования декларативного подхода (Terraform)

### 4.1. Terraform + Docker vs Docker Compose

| Аспект               | Terraform + Docker    | Docker Compose         |
|----------------------|-----------------------|------------------------|
| **State management** | terraform.tfstate     | Нет                    |
| **Drift detection**  | `terraform plan`      | Нет                    |
| **Переносимость**    | Тот же HCL для облака | Только Docker          |
| **Модульность**      | Модули, переменные    | ️ Ограниченная         |
| **Масштабирование**  | `count`, `for_each`   | ️ `deploy.replicas`    |
| **Outputs**          | Структурированные     | Нет                    |
| **Удобство**         | ️ Более verbose       | Компактнее             |

**Почему Terraform, а не Docker Compose:**
1. **Единый инструмент** - тот же Terraform используется для облачной инфраструктуры. Переход dev → prod = смена провайдера
2. **State** - Terraform отслеживает состояние и показывает drift
3. **Планирование** - `terraform plan` показывает изменения ДО применения
4. **Переменные** - `terraform.tfvars` для разных окружений

### 4.2. Путь миграции: Docker → Облако

```
terraform.tfvars (dev)  + main.tf (Docker)  → Локальная среда
terraform.tfvars (prod) + main.tf (Yandex)  → Облачная среда
```

Структура переменных сохраняется - меняется только провайдер и ресурсы.

## 5. Infrastructure as Code: воспроизводимость и масштабируемость

### 5.1. Воспроизводимость

```bash
# Полное развёртывание с нуля
terraform init
terraform apply -auto-approve
# Результат: 12 контейнеров за ~1 минуту

# Полное удаление
terraform destroy -auto-approve
# Результат: чистая система за ~10 секунд

# Повторное развёртывание - идентичный результат
terraform apply -auto-approve
```

### 5.2. Масштабирование

**Добавление Kafka брокера:**
```hcl
# terraform.tfvars
kafka_broker_count = 5  # было 3
```

**Добавление нового домена (фармацевтика):**
```hcl
# Добавить в main.tf
resource "docker_container" "pg_pharma" {
  name  = "${var.project}-pg-pharma"
  image = docker_image.postgres.image_id
  env   = ["POSTGRES_DB=pharma", ...]
  ports { internal = 5432; external = 5437 }
  ...
}
```

### 5.3. Управление состоянием

Terraform хранит состояние в `terraform.tfstate`:
- Отслеживает 12 контейнеров, 10 volumes, 1 network, 7 images
- `terraform plan` показывает расхождения
- `terraform state list` - список всех ресурсов

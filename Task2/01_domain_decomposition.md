# Разделение системы на домены

## 1. Принципы разделения

Разделение на домены выполнено на основе следующих принципов:

1. **Бизнес-ориентированность** - каждый домен соответствует отдельному бизнес-направлению или функции компании
2. **Независимость развития** - изменения в одном домене не требуют изменений в других
3. **Владение данными** - каждый домен является единственным владельцем своих данных
4. **Минимизация связанности** - домены взаимодействуют через чётко определённые контракты (API и события)
5. **Соответствие организационной структуре** - домены отражают структуру подразделений компании (закон Конвея)

---

## 2. Выделенные домены

###  Домен 1: Клинический (Clinic Domain)

**Владелец:** Подразделение «Клиники»

**Ответственность:**
- Управление клиниками (филиалы, кабинеты, оборудование)
- Регистрация и управление данными пациентов (профиль, контакты, страховка)
- Расписание приёмов и записей
- Управление очередями
- Клиентский интерфейс оператора (замена PowerBuilder)

**Данные, которыми владеет домен:**
- Профили пациентов (ФИО, контакты, страховка)
- Расписание приёмов
- Данные о клиниках (адреса, кабинеты, оборудование)
- Записи на приём

**Бизнес-сценарии:**
- Пациент записывается на приём
- Оператор регистрирует нового пациента
- Врач просматривает расписание
- Администратор управляет ресурсами клиники

**Обоснование выделения:**
- Клиники - ядро бизнеса компании, их операционная деятельность должна быть независимой
- Расписание и регистрация пациентов - высоконагруженные процессы, требующие отдельного масштабирования
- Замена PowerBuilder на современный интерфейс возможна без влияния на другие домены
- Организационно соответствует подразделению «Клиники»

**Технологический стек:**
- API: Python/FastAPI или Java/Spring Boot
- БД: PostgreSQL
- Интерфейс: React/Vue.js (замена PowerBuilder)
- Кэш: Redis (для расписания)

---

###  Домен 2: Медицинских данных (Medical Data Domain)

**Владелец:** Подразделение «Клиники» + «ИИ-сервисы»

**Ответственность:**
- Хранение медицинских карт и историй болезней
- Результаты диагностических исследований
- Медицинские снимки и изображения
- Управление доступом к медицинским данным (строгая авторизация)

**Данные, которыми владеет домен:**
- Медицинские карты
- Истории болезней
- Результаты исследований (лабораторные, диагностические)
- Медицинские снимки (DICOM и др.)

**Бизнес-сценарии:**
- Врач просматривает историю болезни пациента
- Лаборатория загружает результаты исследований
- ИИ-сервис запрашивает снимки для анализа
- Врач получает результаты ИИ-анализа

**Обоснование выделения:**
- Медицинские данные подлежат строгому регулированию (HIPAA, ФЗ-152, врачебная тайна)
- Эти данные **НЕ попадают в аналитическую витрину** - требуется физическая изоляция
- Снимки и исследования - большие объёмы данных, требующие специализированного хранения (Object Storage)
- ИИ-сервисы должны иметь контролируемый доступ к медицинским данным через API, а не напрямую к БД

**Технологический стек:**
- API: Python/FastAPI
- БД: PostgreSQL (структурированные данные)
- Object Storage: S3/MinIO (снимки, DICOM)
- Шифрование: AES-256 at rest, TLS in transit

**️ Важно:** Данные этого домена НЕ публикуются в аналитическую витрину. Только агрегированные и обезличенные метрики (количество исследований, типы диагнозов без привязки к пациентам) могут передаваться в аналитический домен.

---

###  Домен 3: Финтех (Fintech Domain)

**Владелец:** Подразделение «Финтех-компания с банковской лицензией»

**Ответственность:**
- Управление счетами клиентов
- Обработка платежей
- Кредитование и займы
- Финансовая история клиентов
- Биллинг за медицинские услуги
- Интеграция с внешними банками и платёжными системами
- Финансовая отчётность

**Данные, которыми владеет домен:**
- Счета клиентов
- Транзакции и платежи
- Кредитные договоры
- Финансовая история
- Тарифы и прайс-листы

**Бизнес-сценарии:**
- Пациент оплачивает медицинские услуги
- Клиент оформляет кредит на лечение
- Бухгалтерия формирует финансовую отчётность
- Интеграция нового платёжного сервиса
- Расчёт стоимости лечения по страховке

**Обоснование выделения:**
- Финтех-компания имеет **банковскую лицензию** - регуляторные требования (PCI DSS, ЦБ) требуют изоляции
- Финансовые данные критичны для бизнеса и подлежат строгому аудиту
- Финтех-направление должно развиваться **независимо** от медицинского
- Организационно соответствует отдельному подразделению с банковской лицензией
- Существующие сервисы на Go/Java могут развиваться без изменений в DWH

**Технологический стек:**
- API: Go/Java (существующие сервисы)
- БД: PostgreSQL (ACID транзакции критичны)
- Очереди: Kafka (гарантированная доставка финансовых событий)
- Безопасность: PCI DSS compliance, шифрование, аудит

---

### Домен 4: ИИ-сервисов (AI Services Domain)

**Владелец:** Подразделение «ИИ-сервисы для медицинских данных»

**Ответственность:**
- Разработка и обучение ML-моделей
- Анализ медицинских снимков
- Предиктивная аналитика (прогнозирование заболеваний)
- Поддержка врачебных решений (Decision Support)
- Мониторинг качества моделей

**Данные, которыми владеет домен:**
- ML-модели (версионированные)
- Результаты предсказаний
- Метрики качества моделей
- Обучающие датасеты (обезличенные)

**Бизнес-сценарии:**
- Врач запрашивает ИИ-анализ снимка пациента
- Data Scientist обучает новую модель на обезличенных данных
- Система автоматически анализирует результаты исследований
- Мониторинг drift моделей и переобучение

**Обоснование выделения:**
- ИИ-сервисы - отдельное подразделение компании с собственной экспертизой
- Требуются специфические ресурсы (GPU, большие объёмы памяти)
- Цикл разработки ML-моделей отличается от обычной разработки (эксперименты, A/B тесты)
- Существующие сервисы на Python могут развиваться независимо
- Доступ к медицинским данным - только через API домена медицинских данных (контролируемый)

**Технологический стек:**
- API: Python/FastAPI
- ML: TensorFlow/PyTorch, MLflow
- Хранилище моделей: S3 + MLflow Model Registry
- Compute: GPU-инстансы (облако)
- Мониторинг: Evidently AI / Whylabs

---

###  Домен 5: Операционный (Operations Domain)

**Владелец:** Головной офис

**Ответственность:**
- Управление персоналом (HR)
- Инвентаризация оборудования и расходных материалов
- Закупки и поставки
- Управление ресурсами компании
- Внутренняя отчётность

**Данные, которыми владеет домен:**
- Данные о сотрудниках (HR)
- Инвентаризационные данные
- Закупки и контракты с поставщиками
- Бюджеты подразделений

**Бизнес-сценарии:**
- HR оформляет нового сотрудника
- Менеджер клиники заказывает расходные материалы
- Закупщик оформляет контракт с поставщиком оборудования
- Руководство анализирует расходы по подразделениям

**Обоснование выделения:**
- Операционные процессы (HR, закупки, инвентаризация) - общие для всей компании
- Не зависят от специфики медицинского или финансового направления
- Могут развиваться независимо (например, внедрение новой HR-системы)
- Данные о персонале и закупках не должны быть доступны из медицинского или финтех домена

**Технологический стек:**
- API: Java/Spring Boot
- БД: PostgreSQL
- Интеграция: Kafka (события о закупках, изменениях в штате)

---

###  Домен 6: Аналитический (Analytics Domain)

**Владелец:** Головной офис (Data Team)

**Ответственность:**
- Витрина данных (Data Mart)
- Портал самообслуживания
- BI-дашборды и отчётность
- Data Catalog
- Data Quality и Data Governance
- Агрегация данных из всех доменов (кроме медицинских карт)

**Данные, которыми владеет домен:**
- Агрегированные и трансформированные данные из всех доменов
- Метаданные (Data Catalog)
- Политики доступа и качества данных
- Кэшированные отчёты и дашборды

**️ НЕ включает:**
- Медицинские карты и истории болезней
- Результаты медицинских исследований
- Персональные медицинские данные

**Бизнес-сценарии:**
- Аналитик строит отчёт по выручке клиник за квартал
- Менеджер просматривает дашборд с KPI
- Руководство анализирует эффективность направлений
- Финансовый директор формирует консолидированную отчётность
- Бизнес-пользователь конструирует собственный отчёт

**Обоснование выделения:**
- Аналитика - кросс-доменная функция, требующая данных из всех доменов
- Портал самообслуживания - ключевая бизнес-цель компании
- Отделение аналитики от операционных систем устраняет конкуренцию за ресурсы (OLTP vs OLAP)
- Data Lakehouse оптимизирован для аналитических запросов (columnar storage)
- Data Governance обеспечивает единые стандарты качества данных

**Технологический стек:**
- Data Lakehouse: Databricks/Snowflake
- BI: Tableau/Looker
- Портал: React/Vue.js
- Data Catalog: DataHub/Amundsen
- ETL: dbt + Apache Airflow
- Data Quality: Great Expectations

---

###  Домен 7: Партнёрский (Partner Integration Domain)

**Владелец:** Головной офис (Integration Team)

**Ответственность:**
- Интеграция с фармацевтическими компаниями
- Интеграция с производителями медицинского оборудования
- Интеграция с внешними банками и платёжными системами
- Управление партнёрскими API
- Стандартизация интеграционных протоколов

**Данные, которыми владеет домен:**
- Каталоги партнёров
- Контракты и SLA с партнёрами
- Логи интеграций
- Маппинг данных (трансформация форматов)

**Бизнес-сценарии:**
- Подключение новой фармацевтической компании к системе закупок
- Интеграция нового производителя оборудования
- Подключение внешнего банка для кредитных продуктов
- Мониторинг доступности партнёрских API

**Обоснование выделения:**
- Компания планирует **активно расширять экосистему** (фармацевтика, электроника)
- Каждый новый партнёр не должен требовать изменений во внутренних доменах
- Стандартизация интеграций снижает стоимость подключения новых партнёров
- Партнёрский домен выступает «адаптером» между внешними и внутренними системами
- Изоляция внешних систем от внутренних повышает безопасность

**Технологический стек:**
- API Gateway: Kong/Apigee
- Адаптеры: Java/Go (микросервисы)
- Очереди: Kafka (асинхронная интеграция)
- Мониторинг: Prometheus + Grafana

## 3. Соответствие доменов организационной структуре

| Подразделение         | Домены                                   |
|-----------------------|------------------------------------------|
| **Головной офис**     | Операционный, Аналитический, Партнёрский |
| **Клиники**           | Клинический, Медицинских данных          |
| **ИИ-компании**       | ИИ-сервисов                              |
| **Финтех-компания**   | Финтех                                   |

Это соответствие обеспечивает:
- Каждое подразделение владеет своими доменами
- Ответственность за данные чётко распределена
- Команды могут развивать свои домены независимо
- Организационные изменения не требуют архитектурных изменений

## 5. Связь доменов с бизнес-сценариями

### Сценарий 1: Обслуживание пациента в клинике

```
Пациент → [Клинический] запись на приём
         → [Мед. данных] врач просматривает историю
         → [ИИ-сервисов] анализ снимков
         → [Мед. данных] сохранение результатов
         → [Финтех] выставление счёта и оплата
```

**Домены:** Клинический → Мед. данных → ИИ → Мед. данных → Финтех

### Сценарий 2: Интеграция нового финтех-сервиса

```
Новый сервис → [Партнёрский] регистрация и настройка API
             → [Финтех] подключение к платёжной системе
             → [Аналитический] добавление метрик в дашборды
```

**Домены:** Партнёрский → Финтех → Аналитический

**Ключевое преимущество:** Не требуется изменений в DWH или других доменах!

### Сценарий 3: ИИ-анализ медицинских данных

```
Врач → [Клинический] инициирует запрос
     → [ИИ-сервисов] запускает анализ
     → [Мед. данных] получает снимки через API
     → [ИИ-сервисов] возвращает результат
     → [Мед. данных] сохраняет результат
     → [Клинический] врач видит результат
```

**Домены:** Клинический → ИИ → Мед. данных → ИИ → Мед. данных → Клинический

### Сценарий 4: Подключение фармацевтической компании

```
Фарм. компания → [Партнёрский] регистрация, настройка API
               → [Операционный] интеграция с закупками
               → [Аналитический] метрики по закупкам
```

**Домены:** Партнёрский → Операционный → Аналитический

**Ключевое преимущество:** Новый партнёр подключается через стандартный API без изменений в других доменах!

## 6. Правила взаимодействия между доменами

### Принцип 1: Владелец данных
Каждый набор данных имеет **ровно одного владельца**. Другие домены могут только читать данные через API.

### Принцип 2: Асинхронность по умолчанию
Межсервисное взаимодействие - через **события (Kafka)**. Синхронные вызовы (REST/gRPC) - только когда требуется немедленный ответ.

### Принцип 3: Data Products
Каждый домен публикует **Data Products** - подготовленные, документированные наборы данных для аналитики.

### Принцип 4: Изоляция медицинских данных
Медицинские карты, истории болезней и результаты исследований **никогда не покидают** домен медицинских данных в сыром виде. Только обезличенные агрегаты.

### Принцип 5: Контрактное взаимодействие
Все API имеют **версионированные контракты**. Изменения обратно совместимы.

## 7. Сравнение с текущей архитектурой

| Аспект                        | Текущая (AS-IS)                    | Целевая (TO-BE)                         |
|-------------------------------|------------------------------------|-----------------------------------------|
| **Хранение данных**           | Всё в одном DWH                    | Каждый домен - своя БД                  |
| **Бизнес-логика**             | В DWH (SQL)                        | В сервисах доменов                      |
| **Интеграция**                | Через ESB (единая точка)           | Kafka + API Gateway (распределённая)    |
| **Добавление нового бизнеса** | Изменения в DWH                    | Новый домен или адаптер в партнёрском   |
| **Масштабирование**           | Вертикальное (больше мощности DWH) | Горизонтальное (масштабирование домена) |

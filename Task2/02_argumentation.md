# Аргументация логики разделения на домены

## 1. Почему именно 7 доменов?

### Принцип разделения

Разделение на домены выполнено на основе трёх ключевых критериев:

1. **Бизнес-функция** - каждый домен соответствует отдельной бизнес-функции компании
2. **Организационная структура** - домены отражают подразделения компании (закон Конвея)
3. **Регуляторные требования** - чувствительные данные изолированы в отдельных доменах

### Почему не меньше доменов?

| Вариант                               | Проблема                                                                                                                                                            |
|---------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Объединить Клинический + Мед. данных  | Нарушение изоляции мед. данных. Операционные данные клиник (расписание, регистрация) имеют другой жизненный цикл и требования к безопасности, чем медицинские карты |
| Объединить Операционный + Клинический | Разные владельцы (Головной офис vs Клиники). HR и закупки - общекорпоративные функции, не специфичные для клиник                                                    |
| Убрать Партнёрский домен              | Потеря стандартизации интеграций. Каждый домен будет самостоятельно интегрироваться с внешними системами - дублирование и хаос                                      |
| Объединить Аналитический с другими    | Конкуренция OLTP и OLAP за ресурсы. Аналитика - кросс-доменная функция, требующая данных из всех доменов                                                            |

### Почему не больше доменов?

| Вариант                                     | Проблема                                                                                          |
|---------------------------------------------|---------------------------------------------------------------------------------------------------|
| Разделить Финтех на Платежи + Кредиты       | Избыточная гранулярность. Оба направления управляются одним подразделением с банковской лицензией |
| Выделить отдельный домен для каждой клиники | Избыточная сложность. Все клиники работают по единым процессам                                    |
| Выделить домен Data Governance              | Data Governance - это функция аналитического домена, а не отдельный бизнес-процесс                |

## 2. Преимущества для бизнеса

### 2.1. Ускорение вывода продуктов (Time-to-Market)

#### Текущая ситуация (AS-IS)
- Любое изменение требует модификации DWH
- Изменения в DWH влияют на все системы
- Цикл разработки: **месяцы**
- Тестирование затрагивает всю систему

#### Целевая ситуация (TO-BE)
- Изменения в домене не влияют на другие домены
- Каждый домен имеет свой цикл разработки
- Цикл разработки: **недели**
- Тестирование ограничено доменом

#### Почему это работает?

1. **Независимые деплои** - каждый домен деплоится отдельно, без координации с другими
2. **Маленькие команды** - команда домена знает свой контекст и принимает решения быстро
3. **Стабильные контракты** - API между доменами версионированы, изменения обратно совместимы
4. **Параллельная разработка** - несколько доменов могут развиваться одновременно

---

#### Что происходит с текущим DWH?

| Этап                  | Действие                                                                  | Результат                          |
|-----------------------|---------------------------------------------------------------------------|------------------------------------|
| **Фаза 1** (0-3 мес)  | DWH продолжает работать, параллельно разворачивается новая инфраструктура | Бизнес не прерывается              |
| **Фаза 2** (3-6 мес)  | Данные первого домена мигрируют из DWH                                    | DWH разгружаются                   |
| **Фаза 3** (6-9 мес)  | Остальные домены мигрируют                                                | DWH используется только для legacy |
| **Фаза 4** (9-12 мес) | DWH выводится из эксплуатации                                             | Полная независимость от DWH        |

#### Конкретные выгоды от ухода от DWH

| Метрика                       | С DWH                    | Без DWH                    | Улучшение        |
|-------------------------------|--------------------------|----------------------------|------------------|
| Время формирования отчёта     | Часы                     | Минуты                     | **95%+**         |
| Стоимость лицензии SQL Server | Высокая                  | $0 (PostgreSQL)            | **100%**         |
| Риск полной остановки         | Высокий (единая точка)   | Минимальный (изоляция)     | **Критичное**    |
| Стоимость изменений           | Высокая (координация)    | Низкая (в домене)          | **70-80%**       |
| Найм специалистов             | Сложно (SQL Server 2008) | Легко (PostgreSQL, Python) | **Значительное** |

### 2.3. Возможность отдельного развития направлений

#### Финтех-направление

**Текущие ограничения:**
- Финтех-сервисы (Go/Java) зависят от DWH для хранения данных
- Изменения в финансовой логике требуют модификации DWH
- Невозможно быстро запускать новые финансовые продукты

**После разделения на домены:**
- Финтех домен имеет **собственную БД** и бизнес-логику
- Новые продукты (кредиты, страховки, рассрочки) запускаются **за недели**
- Интеграция с внешними банками - через Партнёрский домен, без изменений в других доменах
- Соответствие **PCI DSS** обеспечивается изоляцией домена
- Команда финтеха **полностью автономна** в принятии технических решений

#### ИИ-направление

**Текущие ограничения:**
- ИИ-сервисы получают данные черeз ESB - медленно и ненадёжно
- Нет возможности быстро экспериментировать с новыми моделями
- Результаты ИИ-анализа сохраняются в DWH - сложная интеграция

**После разделения на домены:**
- ИИ домен имеет **собственную инфраструктуру** (GPU, S3, MLflow)
- Доступ к медицинским данным - через **контролируемый API** (не напрямую к БД)
- Эксперименты с моделями - **без влияния** на операционные системы
- A/B тестирование моделей - **встроенная возможность**
- Мониторинг drift - **автоматический**

#### Клиническое направление

**Текущие ограничения:**
- Интерфейс оператора (PowerBuilder) - устаревший, сложно модифицировать
- Все данные в DWH - невозможно оптимизировать для операционных нужд
- Расписание и регистрация конкурируют с аналитикой за ресурсы DWH

**После разделения на домены:**
- Современный веб-интерфейс (React/Vue.js) **вместо PowerBuilder**
- Операционная БД оптимизирована для **OLTP** (быстрые транзакции)
- Расписание кэшируется в **Redis** - мгновенный отклик
- Масштабирование под нагрузку - **независимо** от других доменов

#### Партнёрские интеграции (фармацевтика, оборудование)

**Текущие ограничения:**
- Каждая интеграция требует изменений в ESB и DWH
- Нет стандартизированного подхода к подключению партнёров
- Высокая стоимость и длительность интеграции

**После разделения на домены:**
- Партнёрский домен предоставляет **стандартизированные API-адаптеры**
- Новый партнёр подключается через **конфигурацию**, а не разработку
- Внутренние домены **не изменяются** при подключении нового партнёра
- Мониторинг интеграций - **централизованный**

## 3. Снижение рисков

### 3.1. Технические риски

| Риск                              | AS-IS                                 | TO-BE                                       |
|-----------------------------------|---------------------------------------|---------------------------------------------|
| **Отказ хранилища**               | Полная остановка бизнеса (единый DWH) | Отказ одного домена, остальные работают     |
| **Отказ интеграции**              | Полная остановка обмена (единый ESB)  | Kafka с гарантированной доставкой, retry    |
| **Потеря данных**                 | Риск потери всех данных (единая БД)   | Изолированные БД с независимым бэкапом      |
| **Уязвимость безопасности**       | Доступ ко всем данным                 | Изоляция по доменам, минимальные привилегии |
| **Деградация производительности** | Влияет на все системы                 | Изолирована в домене                        |

### 3.2. Бизнес-риски

| Риск                              | AS-IS                             | TO-BE                                    |
|-----------------------------------|-----------------------------------|------------------------------------------|
| **Регуляторные штрафы**           | Мед. и фин. данные смешаны        | Изоляция по доменам, compliance          |
| **Потеря клиентов**               | Медленный сервис (DWH перегружен) | Быстрый отклик (оптимизированные домены) |
| **Отставание от конкурентов**     | Долгий TTM (месяцы)               | Быстрый TTM (недели)                     |
| **Невозможность масштабирования** | Вертикальное (дорого)             | Горизонтальное (гибко)                   |
| **Зависимость от вендора**        | SQL Server 2008 (Microsoft)       | Open source (PostgreSQL, Kafka)          |

### 3.3. Организационные риски

| Риск                      | AS-IS                                             | TO-BE                                     |
|---------------------------|---------------------------------------------------|-------------------------------------------|
| **Найм специалистов**     | SQL Server 2008, PowerBuilder - мало специалистов | PostgreSQL, Python, React - большой рынок |
| **Bus factor**            | Единая команда DWH - критичная зависимость        | Распределённые команды по доменам         |
| **Конфликты приоритетов** | Все изменения через одну команду DWH              | Каждый домен - свои приоритеты            |
| **Обучение**              | Сложная монолитная система                        | Понятные изолированные домены             |

## 4. Заключение

### Ключевые аргументы в пользу разделения на 7 доменов:

1. **Ускорение TTM в 5-15 раз** - новые продукты за недели, а не месяцы
2. **Полная независимость от DWH** - бизнес-логика в доменах, не в хранилище
3. **Независимое развитие направлений** - финтех, ИИ, клиники развиваются автономно
4. **Стандартизированная интеграция партнёров** - фармацевтика и оборудование подключаются за недели
5. **Снижение рисков** - нет единых точек отказа, изоляция чувствительных данных
6. **Экономическая эффективность** - ROI 60-100% в первый год
7. **Соответствие организационной структуре** - домены отражают подразделения компании
8. **Соответствие регуляторным требованиям** - изоляция медицинских и финансовых данных
9. **Масштабируемость** - горизонтальное масштабирование каждого домена
10. **Современные технологии** - уход от устаревших SQL Server 2008 и PowerBuilder

### Риски разделения:

| Риск                             | Митигация                                                 |
|----------------------------------|-----------------------------------------------------------|
| Сложность распределённой системы | Стандартизированные контракты (API, события), мониторинг  |
| Дублирование данных              | Чёткое владение данными, Data Products                    |
| Согласованность данных           | Event-driven архитектура, eventual consistency            |
| Стоимость миграции               | Поэтапная миграция (4 фазы), параллельная работа с legacy |
| Обучение команд                  | Постепенное внедрение, документация, менторинг            |

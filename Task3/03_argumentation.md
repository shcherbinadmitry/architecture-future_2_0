# Аргументация планируемых изменений

## Введение

Каждый этап роадмапа трансформации «Будущее 2.0» обоснован конкретными бизнес-потребностями. В этом документе для каждого этапа описано:
- **Зачем** нужен этот этап с точки зрения бизнеса
- **Как** он влияет на скорость принятия решений, качество сервиса, затраты и масштабирование

---

## Фаза 1: Фундамент (месяцы 1-3)

### Облачная инфраструктура (Terraform, Kubernetes)

**Зачем нужно:**
- Текущая on-premise инфраструктура не позволяет быстро масштабировать ресурсы.
- Закупка нового оборудования занимает месяцы.
- При пиковых нагрузках (например, утренняя запись пациентов) система деградирует.

**Влияние на бизнес:**

| Аспект                        | Без облака                                                               | С облаком                                  |
|-------------------------------|--------------------------------------------------------------------------|--------------------------------------------|
| **Скорость принятия решений** | Запрос на оборудование → согласование → закупка → настройка (2-3 месяца) | Terraform apply → ресурсы за минуты        |
| **Качество сервиса**          | Деградация при пиковых нагрузках                                         | Auto-scaling, стабильная работа            |
| **Затраты**                   | CAPEX: большие единовременные инвестиции в оборудование                  | OPEX: оплата по потреблению, снижение TCO  |
| **Масштабирование**           | Вертикальное (дорого, ограничено)                                        | Горизонтальное (быстро, гибко)             |

---

### Data Lakehouse (Databricks/Snowflake)

**Зачем нужно:**
- Формирование сложных отчётов в текущем DWH занимает **часы**. Это критически замедляет принятие управленческих решений.
- Руководство не может оперативно реагировать на изменения в бизнесе.

**Влияние на бизнес:**

| Аспект                        | DWH (SQL Server 2008)                                      | Data Lakehouse                                          |
|-------------------------------|------------------------------------------------------------|---------------------------------------------------------|
| **Скорость принятия решений** | Отчёт за часы → решение на следующий день                  | Отчёт за минуты → решение сейчас                        |
| **Качество сервиса**          | Аналитика конкурирует с операционными системами за ресурсы | Изолированные compute ресурсы для аналитики             |
| **Затраты**                   | Лицензия SQL Server Enterprise ~$15K/ядро/год              | Оплата по потреблению, columnar storage в 5-10x дешевле |
| **Масштабирование**           | Ограничено мощностью сервера                               | Независимое масштабирование compute и storage           |

---

### Apache Kafka (замена ESB)

**Зачем нужно:**
Текущий ESB (Apache Camel) 
- **единая точка отказа**. При его сбое останавливается весь обмен данными: медицинские данные не передаются, финансовые транзакции не обрабатываются, ИИ-сервисы не работают.
- Это прямой риск для жизни пациентов и финансовых потерь.

**Влияние на бизнес:**

| Аспект                        | ESB (Apache Camel)                                     | Apache Kafka                                       |
|-------------------------------|--------------------------------------------------------|----------------------------------------------------|
| **Скорость принятия решений** | Синхронные вызовы - блокировка при ожидании            | Асинхронные события - мгновенная реакция           |
| **Качество сервиса**          | Отказ ESB = остановка всего бизнеса                    | Отказ одного брокера - система продолжает работать |
| **Затраты**                   | Высокая стоимость поддержки и мониторинга единой точки | Распределённая система, самовосстановление         |
| **Масштабирование**           | Вертикальное (ограничено)                              | Горизонтальное (добавление брокеров)               |

---

### Мониторинг (Prometheus + Grafana)

**Зачем нужно:**
- Сейчас проблемы обнаруживаются **после** жалоб пользователей.
- Нет проактивного мониторинга. 
- Время обнаружения проблемы (MTTD) - часы, время восстановления (MTTR) - часы.

**Влияние на бизнес:**

| Аспект                        | Без мониторинга                               | С мониторингом                                     |
|-------------------------------|-----------------------------------------------|----------------------------------------------------|
| **Скорость принятия решений** | Проблема обнаруживается через часы (жалобы)   | Алерт за секунды                                   |
| **Качество сервиса**          | Пользователи страдают до обнаружения проблемы | Проактивное устранение до влияния на пользователей |
| **Затраты**                   | Высокая стоимость простоев                    | Снижение простоев на 90%+                          |
| **Масштабирование**           | Нет данных для capacity planning              | Метрики для планирования ресурсов                  |

---

## Фаза 2: Первые домены (месяцы 3-7)

### Операционный домен (пилот)

**Зачем нужно:**
Необходимо **доказать работоспособность** новой архитектуры на реальном домене перед миграцией критичных систем (финтех, медицина). Операционный домен выбран как пилот, потому что:
- Наименее критичен для бизнеса (HR, закупки)
- Минимальные регуляторные требования
- Позволяет отработать процесс миграции

**Влияние на бизнес:**

| Аспект                        | Влияние                                                            |
|-------------------------------|--------------------------------------------------------------------|
| **Скорость принятия решений** | HR и закупки работают быстрее (оптимизированная БД)                |
| **Качество сервиса**          | Proof of Concept для всей компании                                 |
| **Затраты**                   | Отработка процесса миграции снижает стоимость последующих миграций |
| **Масштабирование**           | Шаблон для создания новых доменов                                  |

---

### Клинический домен и Клинический портал (замена PowerBuilder)

**Зачем нужно:**
PowerBuilder — операторы клиник и врачи работают с **устаревшим интерфейсом**, который не поддерживает мобильные устройства, онлайн-запись и современный UX. Это снижает эффективность работы и удовлетворённость пациентов. **Клинический портал** (React) становится единым интерфейсом для двух ключевых ролей:
- **Врач** — просмотр расписания, доступ к медицинским картам (через Медицинский домен), запрос ИИ-анализа снимков (через ИИ-домен), просмотр результатов исследований
- **Оператор** — регистрация пациентов, запись на приём, управление очередями, редактирование расписания врачей

**Цепочка систем:**
```
Врач/Оператор → Клинический портал (React) → API Gateway (Kong) → Клинический домен (FastAPI + PostgreSQL + Redis)
                                                                 → Медицинский домен (FastAPI + PostgreSQL + S3)
                                                                 → ИИ-домен (FastAPI + MLflow)
```

**Влияние на бизнес:**

| Аспект                        | PowerBuilder                                  | React (новый интерфейс)                         |
|-------------------------------|-----------------------------------------------|-------------------------------------------------|
| **Скорость принятия решений** | Медленный интерфейс, ограниченные возможности | Быстрый, интуитивный интерфейс                  |
| **Качество сервиса**          | Нет онлайн-записи, нет мобильного доступа     | Онлайн-запись, мобильный доступ для врачей      |
| **Затраты**                   | Высокая стоимость лицензий и поддержки        | Open source (React), большой рынок специалистов |
| **Масштабирование**           | Невозможно добавить новые функции             | Быстрое добавление новых функций                |

---

### Data Catalog (DataHub)

**Зачем нужно:**
Бизнес-пользователи **не знают, какие данные доступны** и где их найти. Все запросы идут через IT-отдел, что создаёт очередь и замедляет работу. Data Catalog - ключевой компонент для self-service аналитики.

**Влияние на бизнес:**

| Аспект                        | Без Data Catalog                          | С Data Catalog                         |
|-------------------------------|-------------------------------------------|----------------------------------------|
| **Скорость принятия решений** | Запрос в IT → ожидание дней               | Поиск в каталоге → результат за минуты |
| **Качество сервиса**          | Нет документации по данным                | Полная документация, lineage, примеры  |
| **Затраты**                   | IT-отдел тратит время на рутинные запросы | 80%+ запросов через self-service       |
| **Масштабирование**           | Каждый новый отчёт - запрос в IT          | Бизнес создаёт отчёты самостоятельно   |

## Фаза 3: Ключевые домены (месяцы 6-10)

### Финтех домен и Финансовый портал

**Зачем нужно:**
Финтех-компания имеет **банковскую лицензию** и подлежит строгому регулированию (PCI DSS, требования ЦБ).
- Сейчас финансовые данные смешаны с медицинскими в одном DWH — это **регуляторный риск**. 
- Запуск новых финансовых продуктов (кредит на лечение, рассрочка) требует изменений в DWH — это занимает месяцы.
- Финансовые специалисты не имеют **специализированного интерфейса** — работают напрямую с DWH или через общие инструменты.

**Финансовый портал** (React) — специализированный веб-интерфейс для финансовых специалистов: управление счетами, обработка платежей, кредитование, биллинг, расчёт стоимости по страховке. Для аналитической отчётности финансовый специалист также использует Портал самообслуживания и BI-инструменты.

**Цепочка систем:**
```
Финансовый специалист → Финансовый портал (React) → API Gateway (Kong) → Финтех домен (Go/Java + PostgreSQL + Kafka)
                      → Портал самообслуживания (React) → Data Lakehouse (Databricks/Snowflake) → BI (Tableau/Looker)
```

**Влияние на бизнес:**

| Аспект                        | Финтех в DWH                      | Отдельный финтех домен + Финансовый портал |
|-------------------------------|-----------------------------------|----------------------------------|
| **Скорость принятия решений** | Новый продукт: 3-4 месяца         | Новый продукт: 2-3 недели        |
| **Качество сервиса**          | Риск нарушения PCI DSS            | Полное соответствие PCI DSS      |
| **Затраты**                   | Высокая стоимость изменений в DWH | Изменения только в финтех домене |
| **Масштабирование**           | Ограничено мощностью DWH          | Независимое масштабирование      |

---

### ИИ домен

**Зачем нужно:**
ИИ-сервисы - ключевое конкурентное преимущество компании. 
- Сейчас они получают данные через ESB (медленно, ненадёжно) и не могут быстро экспериментировать с новыми моделями.
- Цикл разработки ML-модели отличается от обычной разработки - нужны GPU, эксперименты, A/B тесты.

**Влияние на бизнес:**

| Аспект                        | ИИ через ESB/DWH                       | Отдельный ИИ домен                         |
|-------------------------------|----------------------------------------|--------------------------------------------|
| **Скорость принятия решений** | Новая модель: 2-3 месяца               | Новая модель: 1-2 недели                   |
| **Качество сервиса**          | Нет мониторинга drift, риск деградации | MLflow: мониторинг, версионирование, откат |
| **Затраты**                   | GPU on-premise (дорого, простаивают)   | GPU в облаке (оплата по потреблению)       |
| **Масштабирование**           | Ограничено оборудованием               | GPU-инстансы по требованию                 |

---

### Домен медицинских данных

**Зачем нужно:**
Медицинские данные (карты, истории болезней, снимки) подлежат **строжайшему регулированию** (HIPAA, ФЗ-152, врачебная тайна).
- Сейчас они хранятся в общем DWH вместе с финансовыми и операционными данными - это **критический риск** для compliance. 
- Кроме того, эти данные **НЕ должны попадать в аналитическую витрину**.

**Влияние на бизнес:**

| Аспект                        | Мед. данные в DWH                               | Отдельный домен                              |
|-------------------------------|-------------------------------------------------|----------------------------------------------|
| **Скорость принятия решений** | Врач ждёт загрузки данных из перегруженного DWH | Быстрый доступ через оптимизированный API    |
| **Качество сервиса**          | Риск утечки мед. данных                         | Изоляция, шифрование, контроль доступа       |
| **Затраты**                   | Штрафы за нарушение compliance (миллионы)       | Соответствие регуляторам                     |
| **Масштабирование**           | Снимки в SQL Server (неэффективно)              | Object Storage (S3) - оптимально для снимков |

---

### Партнёрский домен

**Зачем нужно:**
Компания планирует **интегрировать фармацевтические компании и производителей оборудования**.
- Сейчас каждая интеграция требует изменений в ESB и DWH - это дорого и долго. 
- Нужен стандартизированный подход.

**Влияние на бизнес:**

| Аспект                        | Интеграция через ESB/DWH            | Партнёрский домен                       |
|-------------------------------|-------------------------------------|-----------------------------------------|
| **Скорость принятия решений** | Подключение партнёра: 4-6 месяцев   | Подключение: 3-4 недели                 |
| **Качество сервиса**          | Каждая интеграция уникальна         | Стандартизированные API-адаптеры        |
| **Затраты**                   | Высокая стоимость каждой интеграции | Переиспользование адаптеров             |
| **Масштабирование**           | Каждый партнёр - отдельный проект   | Стандартный процесс для любого партнёра |

## Фаза 4: Портал и аналитика (месяцы 8-12)

### Портал самообслуживания

**Зачем нужно:**
Это **ключевая бизнес-цель** компании. 
- Сейчас все запросы на отчёты идут через IT-отдел, что создаёт очередь и замедляет принятие решений.
- Бизнес-пользователи должны иметь возможность самостоятельно работать с данными.

**Влияние на бизнес:**

| Аспект                        | Без портала                 | С порталом                       |
|-------------------------------|-----------------------------|----------------------------------|
| **Скорость принятия решений** | Запрос в IT → дни/недели    | Self-service → минуты            |
| **Качество сервиса**          | Ограниченный набор отчётов  | Любой отчёт по любым срезам      |
| **Затраты**                   | IT-отдел перегружен рутиной | 80%+ запросов через self-service |
| **Масштабирование**           | Каждый новый отчёт - проект | Бизнес создаёт отчёты сам        |

---

### BI-платформа (Tableau/Looker)

**Зачем нужно:**
Текущая Power BI тесно привязана к SQL Server и имеет ограниченные возможности self-service.
- Для полноценной работы с Data Lakehouse нужна BI-платформа с нативной интеграцией.

**Влияние на бизнес:**

| Аспект                        | Power BI + SQL Server         | Tableau/Looker + Lakehouse   |
|-------------------------------|-------------------------------|------------------------------|
| **Скорость принятия решений** | Дашборды обновляются медленно | Real-time дашборды           |
| **Качество сервиса**          | Ограниченный self-service     | Полноценный self-service     |
| **Затраты**                   | Лицензия Microsoft            | Оптимизированная стоимость   |
| **Масштабирование**           | Ограничено SQL Server         | Масштабируется с Lakehouse   |

---

### Data Governance

**Зачем нужно:**
Без контроля качества данных бизнес-пользователи **не будут доверять** отчётам. 
- Если в дашборде неверные цифры - руководство вернётся к запросам в IT. 
- Data Governance - фундамент доверия к данным.

**Влияние на бизнес:**

| Аспект                        | Без Data Governance                          | С Data Governance                           |
|-------------------------------|----------------------------------------------|---------------------------------------------|
| **Скорость принятия решений** | Недоверие к данным → перепроверка → задержки | Доверие к данным → быстрые решения          |
| **Качество сервиса**          | Ошибки в отчётах → неверные решения          | Автоматические проверки → корректные данные |
| **Затраты**                   | Стоимость исправления ошибок                 | Предотвращение ошибок                       |
| **Масштабирование**           | Качество падает с ростом данных              | Автоматический контроль при любом объёме    |

---

### Вывод Legacy

**Зачем нужно:**
Поддержка устаревших систем (SQL Server 2008, PowerBuilder, Apache Camel) стоит существенных денег и создаёт **критические риски безопасности**. 

**Влияние на бизнес:**

| Аспект                        | С Legacy                                 | Без Legacy                      | 
|-------------------------------|------------------------------------------|---------------------------------|
| **Скорость принятия решений** | Команды тратят время на поддержку legacy | Фокус на развитии новых функций |
| **Качество сервиса**          | Уязвимости безопасности                  | Современные, защищённые системы |
| **Затраты**                   | ~ Деньги на лицензии и поддержку         | $0 на legacy                    |
| **Масштабирование**           | Legacy ограничивает возможности          | Полная свобода развития         |

## Заключение

Каждый этап роадмапа **обоснован конкретной бизнес-потребностью** и приносит измеримую ценность:

1. **Фаза 1 (Фундамент)** - устраняет критические риски (единые точки отказа) и создаёт инфраструктуру для трансформации
2. **Фаза 2 (Первые домены)** - доказывает работоспособность архитектуры и начинает формировать аналитическую витрину
3. **Фаза 3 (Ключевые домены)** - обеспечивает независимое развитие направлений и compliance
4. **Фаза 4 (Портал)** - реализует ключевую бизнес-цель - портал самообслуживания
